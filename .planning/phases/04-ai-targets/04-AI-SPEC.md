## 1. System Classification

**System Type:** Structured Content Generation

**Description:**
A Supabase Edge Function (Deno/TypeScript) calls Claude claude-sonnet-4-6 with a user's PCOS profile to generate personalized daily macro targets (protein, fiber, GL ceiling, added sugar, calorie range, P:C ratio) and an Insulin Balance score (0–100) with a 1–2 sentence narrative. The output is a strict JSON object persisted to `ai_daily_targets`. The system runs once per profile change, not per dashboard load. Users are women with PCOS managing insulin resistance through nutrition.

**Critical Failure Modes:**
1. **Medical overreach** — Claude makes a diagnosis, recommends specific supplements with dosages, or gives drug interaction advice (violates AI-05 and exposes Bloom to medical-device liability)
2. **Structurally invalid output** — Claude returns malformed JSON, missing fields, or NaN/null for numeric targets (breaks dashboard rendering; user sees no targets at all)
3. **Biologically implausible targets** — Claude returns values outside safe ranges (e.g., protein_g < 40, calorie_max < 1000, gl_target > 500) that could harm a real user following the advice
4. **Inadequacy framing** — narrative uses deficit language ("you're eating too much", "you've failed") violating CLAUDE.md rule 6 and the PCOS user's psychological safety
5. **API key exposure** — ANTHROPIC_API_KEY leaks into client bundle via Vite env file (violates AI-06 and CLAUDE.md rule 3)

## 1b. Domain Context

**Industry Vertical:** Women's health / PCOS nutrition management

**User Population:** Women aged 18–45 with Polycystic Ovary Syndrome (PCOS) — confirmed, suspected, or self-managing. Most have some degree of insulin resistance. Many have had negative experiences with diet culture and calorie restriction. Using app as an alternative to expensive dietitian appointments.

**Stakes Level:** Medium-High

**Output Consequence:** User reads AI-generated macro targets and adjusts their daily food choices to manage a chronic medical condition (insulin resistance). Incorrect targets may worsen symptoms, cause anxiety, or delay appropriate medical care. The app is not a medical device, but users may treat the advice as authoritative.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|-----------|----------------------|-------------------|--------|--------|
| Protein floor | ≥ 90g/day for 1600 kcal (ensures satiety, glucagon balance) | < 60g protein for any profile (insufficient for insulin regulation) | High | PCOS Nutrition Center guidelines |
| Fiber floor | ≥ 25g/day minimum; 35g preferred for insulin resistance | < 20g fiber (insufficient for glycemic buffer) | High | ADA fiber recommendations for IR |
| GL ceiling | 80–110 GL units/day for weight management profile; up to 130 for maintenance | GL > 150 (no benefit for insulin resistance) or < 60 (overly restrictive) | High | Sydney University GI database |
| Calorie range | 1400–2200 kcal depending on height/weight; ≥ 200 kcal spread between min and max | < 1200 kcal min (starvation-level) or > 2800 kcal max for weight loss goal | Critical | PCOS Society nutritional guidelines |
| Narrative tone | "Today's targets support stable energy and steady insulin levels." | "You need to reduce your intake." or "Your diet is causing your symptoms." | High | PCOS mental health research (Cooney et al., 2017) |
| Insulin Balance score | Score 65–85 for typical confirmed-PCOS weight-loss profile | Score < 30 (discourages the user) or > 95 (false reassurance) | Medium | Clinical judgment — no external standard |

### Known Failure Modes in This Domain

1. **Supplement dosage advice**: Claude may suggest Inositol, Berberine, or Magnesium with specific dosages — these are popular in PCOS communities but must never be recommended by an AI without physician oversight
2. **Calorie restriction advocacy**: PCOS users are disproportionately affected by eating disorder risk; any framing around eating "less" or "restricting" is harmful
3. **Cycle phase advice without data**: If Claude infers cycle phase from the prompt, it may give cycle-specific targets without having actual cycle data — Phase 4 does not pass cycle data so Claude must not assume it
4. **Medication interactions**: Metformin is common in PCOS — Claude must not advise on how food interacts with Metformin or other PCOS medications
5. **Weight loss promises**: Claiming the targets will produce weight loss creates medical liability; framing must be "supports insulin balance" not "helps you lose weight"

### Regulatory / Compliance Context

- **Not a medical device (v1):** Bloom is a wellness app, not a regulated medical device. This status is contingent on the system prompt guardrails. If Claude produces diagnostic language, Bloom may inadvertently become a medical device under FDA/CE rules.
- **GDPR:** Profile data (age, weight, health condition) sent to Claude API is health-adjacent PII. The prompt must not include raw identifiable data beyond what's needed. User ID should never appear in the Claude prompt.
- **HIPAA:** Likely not a covered entity for v1, but pending legal review (per STATE.md). Edge Function must not log the full Claude prompt/response to any monitoring system that stores PII.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| PCOS-specialist registered dietitian | Calibrate rubrics for macro targets; label reference dataset; spot-check biologically implausible outputs |
| PCOS mental health practitioner | Review narrative tone; flag deficit framing or anxiety-inducing language |
| Engineer (Bloom team) | JSON schema validation; range checks; guardrail enforcement; production monitoring |

## 2. Framework Decision

**Selected Framework:** Anthropic TypeScript SDK (direct API call)

**Version:** `@anthropic-ai/sdk` latest stable (imported via `https://esm.sh/@anthropic-ai/sdk` in Deno)

**Rationale:**
Phase 4 is a single-turn, single-model API call that returns a structured JSON object. There is no retrieval, no multi-step reasoning, no agent loop, and no state management beyond what Supabase already handles. Every orchestration framework (LangChain, LangGraph, CrewAI) adds abstraction overhead, Python dependencies, and complexity that would need to be ported to Deno/TypeScript — without providing any benefit for a function that makes exactly one API call. The direct SDK is the right choice.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain TypeScript | Abstraction overhead for a single API call; no retrieval or chaining needed; adds ~40KB to bundle |
| LangGraph TypeScript | Graph-based stateful workflows — overkill for one API call; steeper learning curve without payoff |
| CrewAI | Python only; no Deno support; multi-agent patterns irrelevant for single-turn generation |
| Vercel AI SDK | Designed for streaming UI responses; Supabase Edge Function context makes it redundant |

**Vendor Lock-In Accepted:** Yes — Bloom is Claude-committed per PROJECT.md and CLAUDE.md. This is a conscious, documented trade-off.

## 3. Framework Quick Reference

### Installation (Deno/Edge Function)
```typescript
// No npm install needed — import via esm.sh CDN (same pattern as existing Edge Functions)
import Anthropic from 'https://esm.sh/@anthropic-ai/sdk'
```

### Core Imports
```typescript
import Anthropic from 'https://esm.sh/@anthropic-ai/sdk'
import { createClient } from 'https://esm.sh/@supabase/supabase-js@2'
```

### Entry Point Pattern
```typescript
const client = new Anthropic({ apiKey: Deno.env.get('ANTHROPIC_API_KEY')! })

const response = await client.messages.create({
  model: 'claude-sonnet-4-6',
  max_tokens: 512,
  temperature: 0,
  system: SYSTEM_PROMPT,
  messages: [{ role: 'user', content: buildUserPrompt(profile) }],
})

const text = response.content[0].type === 'text' ? response.content[0].text : ''
const targets = JSON.parse(text) // wrap in try/catch
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `client.messages.create` | Single API call, returns `Message` | Every generation call |
| `system` parameter | Persistent instructions not visible to user | System prompt with guardrails, output format spec |
| `temperature: 0` | Deterministic output | Structured JSON generation — eliminates randomness |
| `max_tokens: 512` | Response length cap | Macro targets + 2-sentence narrative fit in ~300 tokens; 512 is safe ceiling |
| `response.content[0]` | First content block | Always check `.type === 'text'` before accessing `.text` |

### Common Pitfalls
1. **JSON parse failure silent swallowing**: `JSON.parse()` throws synchronously — always wrap in try/catch and return HTTP 500 on failure; never return partial data
2. **Temperature != 0 for structured output**: Non-zero temperature causes JSON syntax variations that break parsing
3. **Deno esm.sh import caching**: Deno caches the import on first deploy; if the SDK version changes, the cached URL must be invalidated via a new deploy
4. **`content[0]` assumption**: Claude may return multiple content blocks in rare cases; always index safely and type-check `.type`
5. **Blocking the Deno event loop**: `await client.messages.create()` is async — never use sync wrappers

### Recommended Project Structure
```
supabase/functions/generate-targets/
└── index.ts          ← Deno.serve entry, JWT auth, profile fetch, Claude call, DB insert
```

## 4. Implementation Guidance

**Model Configuration:**
- Model: `claude-sonnet-4-6`
- Temperature: `0` (deterministic — required for reliable JSON)
- Max tokens: `512` (targets + 2-sentence narrative fit in ~300 tokens)
- Stop sequences: none needed (JSON terminates naturally)

**Core Pattern:**
Single-turn message exchange with structured JSON output. System prompt defines the exact JSON schema; user prompt injects profile data. Response is parsed, validated against expected schema, and inserted to `ai_daily_targets`. No streaming needed — function blocks until full JSON is available.

**Tool Use:**
None. Claude does not use tools in this function. All data (profile) is injected directly into the prompt.

**State Management:**
Stateless per-call. Supabase `ai_daily_targets` table is the persistent state. The Edge Function reads profile from DB, calls Claude, writes result to DB, and returns the result. No in-memory or Redis state.

**Context Window Strategy:**
Profile data is small (~200 tokens). System prompt + profile + few-shot example fits comfortably within 4K tokens. No chunking or summarization needed. If additional food/symptom context is added in a future phase, monitor total prompt size.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic / Zod (TypeScript equivalent)

Since this is TypeScript/Deno, use a validation function instead of Pydantic. Validate all required fields and ranges before inserting to DB:

```typescript
interface AITargetsOutput {
  protein_g: number      // [40, 300]
  fiber_g: number        // [15, 80]
  gl_target: number      // [40, 200]
  added_sugar_g: number  // [10, 60]
  calorie_min: number    // [1000, 2500]
  calorie_max: number    // [1200, 3000]
  pc_ratio_target: number // [0.15, 0.60]
  insulin_score: number  // [0, 100]
  narrative: string      // non-empty, < 300 chars
  key_factors: string[]  // non-empty array
}

function validateTargets(raw: unknown): AITargetsOutput {
  // Assert all fields present, types correct, values in range
  // Throw on any violation — caller returns HTTP 500
}
```

### Async-First Design

Deno's `Deno.serve` handler is already async. The Claude SDK call is `await`-based. No special async handling needed. Do NOT use `Promise.all` for the Claude call + DB insert — insert only after successful parse and validation.

### Prompt Engineering Discipline

- **System prompt** (never changes): guardrails, output schema, persona, examples of good vs. bad output
- **User prompt** (per-call): profile data only, serialized as readable key-value pairs (not raw JSON — improves Claude's reading)
- **Few-shot**: include ONE example of valid output in the system prompt so Claude has a structural reference
- **Token budget**: keep user prompt under 300 tokens; system prompt under 800 tokens

### Context Window Management

Profile data is trivially small. No context management needed for v1. If Phase 5 adds food logs to the prompt, add a hard cap: last 7 days of food_logs (≤ 100 token summary) to stay under 2K tokens.

### Cost and Latency Budget

- **Per-call cost**: ~`$0.003` (claude-sonnet-4-6 pricing: ~300 input tokens + ~200 output tokens)
- **Latency**: 2–4 seconds typical for claude-sonnet-4-6 at temperature 0
- **Call frequency**: Once per profile change (not per dashboard load) — typical user may trigger 5–20 calls total in the app's lifetime
- **Caching**: Result cached in `ai_daily_targets`; Phase 04-02 hook prevents redundant calls
- **No streaming**: Blocking await is correct here — Edge Function waits for full JSON before returning

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail) | Measurement Approach | Priority |
|-----------|-------------------|---------------------|----------|
| JSON schema compliance | All 10 fields present, correct types, no null/NaN | Code — `validateTargets()` function | Critical |
| Value range safety | All numeric fields within safe biological ranges (see 1b) | Code — range checks in `validateTargets()` | Critical |
| Guardrail compliance | No diagnosis, supplement dosages, drug interactions, weight loss promises | Code (regex for "diagnose", "mg/day", "Metformin") + LLM judge | Critical |
| Narrative tone | Adequacy framing, no deficit language, ≤ 2 sentences, ≤ 300 chars | Code (char count) + LLM judge (tone rubric) | High |
| Nutritional plausibility | Protein floor ≥ 90g for weight loss; calorie_min ≥ 1400; fiber ≥ 25g | Code — profile-conditional range checks | High |
| Profile responsiveness | Different PCOS types and goals produce meaningfully different outputs | Human eval — spot check 5 profiles | Medium |
| Insulin score coherence | Score correlates with target restrictiveness: lower GL ceiling → higher score | LLM judge with rubric | Medium |

### Eval Tooling

**Primary Tool:** Promptfoo (CLI, open-source) for prompt regression testing in CI

**Secondary:** Code-based validators in `validateTargets()` run on every call in production (zero-cost, zero-latency checks)

### Reference Dataset

**Size:** 10 synthetic profiles (start small per ai-evals.md guidelines)

**Composition:**
- 2× confirmed PCOS, insulin-resistance type, weight loss goal, BMI 28–32
- 2× suspected PCOS, weight maintenance goal, BMI 22–25
- 2× managing symptoms, high-protein preference, BMI 24–26

**Labeling:**
- For range checks: engineer-labeled (deterministic)

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| JSON parse failure | `JSON.parse()` throws | Return HTTP 500; client falls back to STATIC_TARGETS |
| Schema validation failure | Missing/null required field or type error | Return HTTP 500; client falls back to STATIC_TARGETS |
| Biologically unsafe range | Any value outside safe bounds in `validateTargets()` | Return HTTP 500; log the raw Claude response for investigation |
| Forbidden content (regex) | Response text contains "diagnos", "mg/day", "prescri", "Metformin", "dosage" | Return HTTP 500; log for prompt review |
| Calorie below floor | calorie_min < 1200 | Return HTTP 500 — never deliver starvation-level targets |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Narrative tone quality | Sample 10% of generated rows monthly; LLM judge against tone rubric | Update system prompt; bump prompt_version to invalidate cache |
| Target plausibility drift | Compare generated targets against published PCOS guidelines quarterly | Review with RD consultant; update few-shot examples |
| Guardrail bypass attempts | Alert on any HTTP 500 from forbidden-content guardrail | Immediate system prompt review |

## 7. Production Monitoring

**Tracing Tool:** Supabase Edge Function logs (built-in) for latency and error rates. No external tracing platform in Phase 4 — add Langfuse or Arize Phoenix in Phase 5 when usage volume warrants it.

**Key Metrics to Track:**
1. `generate-targets` Edge Function error rate (target: < 1%)
2. Average latency per call (target: < 5s p95)
3. Claude API availability (monitor via Supabase Edge Function logs)
4. Cache hit rate in `useAITargets` hook (how often clients skip the Edge Function call)
5. Guardrail trigger count per day (any non-zero = prompt review needed)

**Alert Thresholds:**
- Error rate > 5% in any 1-hour window → investigate Claude API status
- Any guardrail trigger (forbidden content or unsafe range) → immediate async investigation
- Latency p95 > 10s → check Claude API status + Edge Function cold start

**Smart Sampling Strategy:**
- Every HTTP 500 response: log `{ user_id_hash, error_type, raw_response_excerpt }` — not full profile data (GDPR)
- Monthly: query `ai_daily_targets` for rows with `insulin_score < 30` or `insulin_score > 95` for plausibility review
- No smart sampling system needed at Phase 4 volume — manual review is sufficient
