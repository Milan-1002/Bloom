<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase Auth JWT → RLS | Every DB query from authenticated users carries a JWT; RLS policies evaluate (select auth.uid()) against user_id |
| client → usda_foods | usda_foods has no RLS; any authenticated user can SELECT — this is intentional (shared food cache) |
| trigger → profiles | handle_new_user runs as security definer — it inserts a profile row automatically on signup; client cannot INSERT directly |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | Cross-user data access | mitigate | RLS policies on all 5 user tables use (select auth.uid()) = user_id. Verified in migration. Smoke-test: attempt cross-user SELECT in Supabase SQL editor returns 0 rows. |
| T-02-02 | Tampering | RLS with-check bypass | mitigate | All INSERT/UPDATE policies include WITH CHECK clause in addition to USING clause. |
| T-02-03 | Elevation of Privilege | profiles INSERT from client | mitigate | No INSERT policy for authenticated role on profiles. Only the security-definer trigger can insert. Client calls UPDATE only during onboarding. |
| T-02-04 | Denial of Service | usda_foods shared cache poisoning | accept | usda_foods has SELECT-only grant to authenticated. INSERT/UPDATE requires service role (only Edge Functions). |
| T-02-SC | Tampering | npm/supabase CLI installs | mitigate | supabase CLI is the official Supabase binary. Packages verified in plan 01-01 legitimacy audit. |
</threat_model>
