<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input → supabase.auth.signUp() | Email and password from form fields; validated by Zod before submission |
| Supabase email link → /auth/callback | Token in URL is validated by Supabase SDK; client does not handle raw JWT |
| session → AuthContext | Session object comes from Supabase SDK; treated as trusted after SDK validates JWT |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Elevation of Privilege | Email verification bypass | mitigate | D-05: CheckInboxScreen has no navigation path to app screens. AuthCallbackScreen only navigates to onboarding after session.user.email_confirmed_at is non-null. |
| T-03-02 | Information Disclosure | Email enumeration on sign-up | accept | Supabase Auth returns generic error messages by default. Do not show "user already exists" — show "check your email" for all sign-up outcomes. |
| T-03-03 | Spoofing | Password reset link reuse | accept | Supabase handles token expiry (1h default) and single-use enforcement. Client does not store reset tokens. |
| T-03-04 | Elevation of Privilege | Flash-redirect auth bypass | mitigate | AuthProvider returns null while loading=true. RequireAuth guard (plan 01-04) only evaluates after loading is false. |
| T-03-05 | Tampering | Resend spam | mitigate | Client-side 60s cooldown on resend button. Supabase server also enforces rate limiting. Both layers required (client = UX; server = enforcement). |
| T-03-SC | Tampering | npm package installs | mitigate | All packages verified in plan 01-01 legitimacy audit. No new packages in this plan. |
</threat_model>
